# 3주차 RAG 평가 과제 계획

작성일: 2026-11-11

이 문서는 인터뷰에서 합의한 개발 방식, 기록 방식, 평가 질문 구성을 정리한 계획입니다. 구현과 평가 실행은 아직 진행하지 않았습니다. 원문 검토 후 확정한 질문 10개와 골든 데이터, 평가 기준, Judge 프롬프트, 파일 구조와 JSON·CSV 필드 계약은 [EVALUATION_SPEC.md](EVALUATION_SPEC.md)에 정리했습니다.

## 1. 목표와 기존 과제의 피드백

2주차에 사용한 동원파츠의 정정 증권신고서 PDF를 대상으로 기존 RAG의 성능을 먼저 측정합니다. 기존 코드를 유지하면서 평가 기능을 추가하고, 첫 평가 결과를 향후 개선 전후 비교의 기준으로 사용합니다.

2주차 제출 기록은 `origin/week-02/DChanHong`의 `week-02/DChanHong/`를 기준으로 확인했습니다.

| 기존 사례 | 확인한 결과 | 3주차에 이어갈 평가 기준 |
|---|---|---|
| Q1: 공모가격 정정 전후 비교 | 희망가격과 확정가격을 구분했습니다. | 정정 전후와 가격의 성격을 정확하게 구분합니다. |
| Q2: 공모자금 사용 계획 비교 | 금액·단위·증감은 정확했지만 일부 청크가 표 중간부터 시작했습니다. | 금액·단위·계산의 정확성과 표 제목·단위·열 이름의 보존 여부를 확인합니다. |
| Q3: 상장 1년 후 종가와 수익률 | 확인 불가를 안내했지만 관련 없는 검색 결과까지 인용했습니다. | 답변 범위 준수와 인용의 적절성을 분리하여 평가합니다. |

기존 프롬프트에도 무관한 근거를 인용하지 말라는 지침이 있었으므로, 지침의 존재보다 실제 준수 여부를 확인합니다. 기존 Q1~Q3는 새 평가 문항으로 재사용하지 않습니다.

## 2. 개발 범위와 위치

개발 위치는 `week-03/DChanHong/`입니다. 이후 구현 단계에서 2주차 코드를 이 위치로 복사하여 기준 버전으로 사용하고, 평가·기록 기능을 추가합니다. 2주차 제출물은 보존합니다.

첫 평가에서는 기존 검색·답변 생성 동작과 자연어 답변 형식을 유지합니다. 구조화된 `status`를 RAG 출력에 추가하거나 청킹·인용 방식을 개선하는 작업은 첫 평가 이후의 선택 범위입니다.

### 필수 범위

1. 새로운 평가 질문 10개와 골든 데이터셋을 준비하고 원문과 대조하여 확정합니다.
2. 기존 RAG로 질문당 1회, 총 10회 실행하여 결과를 저장합니다.
3. 저장된 결과에 자동 평가를 수행합니다.
4. 사람이 10개 문항 전체를 원문과 대조하여 최종 판정을 기록합니다.
5. 전체 결과를 CSV로 정리하고 대표 실패 사례를 분석합니다.

### 선택 범위

- 실패 원인에 따라 청킹·인용·출력 구조 등을 개선합니다.
- 개선 후 동일한 평가 기준으로 재평가하여 전후를 비교합니다.
- 반복 실행으로 응답의 일관성을 검증합니다.

첫 평가는 문항당 1회이므로 반복 실행의 안정성까지 검증한 것으로 해석하지 않습니다. 실패가 발견되지 않으면 통과 판단의 근거와 아직 검증하지 못한 상황을 기록합니다.

## 3. 평가 질문 10개 구성

질문 범위는 공모가격·공모조건·자금 사용 계획을 중심으로 정합니다. 기존 Q1~Q3와 다른 질문을 새로 작성하되, 기존 피드백의 평가 기준은 유지합니다.

| 답변 가능 유형 | 주제 또는 상황 | 문항 수 | 주요 검증 내용 |
|---|---|---:|---|
| 답변 가능 | 공모가격 | 2 | 희망가격·확정가격, 정정 전후 구분 |
| 답변 가능 | 공모조건 | 2 | 문서에 명시된 조건과 정정 내용의 정확성 |
| 답변 가능 | 자금 사용 계획 | 2 | 항목별 금액·단위·계산, 계획과 실적 구분 |
| 답변 불가 | 문서 작성 이후의 실제 결과 | 1 | 근거 없이 추정하지 않고 확인 불가를 안내하는지 |
| 답변 불가 | 문서에 없는 세부 정보 | 1 | 관련 정보와 실제 답변 근거를 구분하는지 |
| 부분 답변 가능 | 공모 정보와 문서 이후의 실제 결과를 함께 질문 | 1 | 확인 가능한 공모 정보만 근거와 함께 답하는지 |
| 부분 답변 가능 | 자금 사용 계획과 확인되지 않은 실제 집행 결과를 함께 질문 | 1 | 계획은 설명하고 확인되지 않은 실적은 구분하는지 |
| **합계** | **답변 가능 6개·답변 불가 2개·부분 답변 가능 2개** | **10** | |

이 표는 질문 설계의 배분입니다. 확정한 Q01~Q10의 질문 원문·골든 답변·근거 위치·통과 조건은 [상세 평가 설계](EVALUATION_SPEC.md)에 기록했습니다. 검색된 일부 청크에 정보가 없다는 사실만으로 문서 전체에 정보가 없다고 판정하지 않습니다.

## 4. 골든 데이터셋 준비

RAG 실행 전에 사람이 다음 내용을 작성하고 원문과 대조하여 확정합니다.

- 문항 ID와 질문
- 기대 답변과 포함해야 할 핵심 정보
- 근거 문서·PDF 페이지·구절 또는 위치
- 기대 답변 가능 유형: 답변 가능, 답변 불가, 부분 답변 가능
- 내용의 정확성·인용의 적절성·답변 범위 준수에 대한 문항별 통과 조건
- 필요한 경우 금액·단위·정정 구분·계산식과 허용 가능한 표현

답변 불가 또는 부분 답변 가능 문항은 확인 가능한 부분과 확인 불가능한 부분을 명시합니다. 문서에 없는 정보에 대해 근거 구절을 임의로 만들지 않습니다.

기대 답변과 평가용 라벨·기준은 RAG의 검색 문서나 답변 생성 입력에 포함하지 않습니다. 첫 평가에 사용한 데이터셋과 기준을 식별할 수 있도록 보존하며, 변경 시 이력을 남깁니다.

## 5. 개발 흐름

### 1단계: 질문 실행과 결과 저장

확정된 10개 질문을 기존 RAG에 입력하고 검색 결과, 실제 생성 모델에 전달한 컨텍스트, 자연어 답변을 저장합니다. 답변 생성 모델에 골든 데이터셋의 정답을 전달하지 않습니다.

기존 코드의 `execution_status`는 실행 완료 여부를 뜻하며 정답 여부와 구분합니다. 답변 가능 유형과 실제 동작의 일치 여부는 평가 결과에 기록합니다.

### 2단계: 저장된 결과 자동 평가

RAG 실행과 평가를 분리합니다. 평가 기준을 수정하거나 평가 중 오류가 발생했을 때, RAG를 다시 실행하지 않고 저장된 동일 답변을 재평가할 수 있도록 구성합니다.

| 평가 수단 | 담당 범위 |
|---|---|
| Ragas | 검색 근거의 관련성·충분성, 답변의 근거 충실성 |
| 별도 규칙 검사와 LLM Judge | 금액·단위·정정 전후, 인용의 적절성, 답변 범위 준수 |
| 사람 | 전체 10개 문항을 원문과 대조하고 최종 판정 확정 |

Ragas 지표는 Context Precision, Context Recall, Faithfulness, Answer Relevancy로 확정했습니다. 문항별 적용 범위와 입력, 규칙 검사와 Judge의 역할은 [상세 평가 설계](EVALUATION_SPEC.md)를 따릅니다. 별도 Judge는 생성 모델과 다른 `gpt-5.4-2026-03-05`를 사용하고, 프롬프트는 `judge_v1`, 출력 형식은 `judge_result_v1`로 고정합니다. Ragas용 평가 LLM과 임베딩 모델은 별도로 확정할 예정입니다.

### 3단계: 사람 검토와 CSV 정리

사람이 원문·질문·검색 근거·실제 전달 컨텍스트·답변을 대조합니다. 자동 평가 결과는 그대로 보존하고 사람의 판정, 근거, 불일치 이유를 별도로 기록합니다.

최종 통과 여부는 사람의 검토로 확정합니다. 기준 자체가 모호했다면 기준을 수정한 이유와 이력을 남깁니다.

## 6. 문항별 통과 기준

| 평가 항목 | 통과 조건 |
|---|---|
| 내용의 정확성 | 질문에 필요한 사실·금액·단위·계산·정정 구분이 정확합니다. 답변 불가 부분은 값을 추정하지 않습니다. |
| 인용의 적절성 | 필요한 핵심 주장에 근거를 연결하고, 각 인용은 연결된 내용을 실제로 뒷받침합니다. 관련 없는 인용을 붙이지 않습니다. |
| 답변 범위 준수 | 답할 수 있는 내용은 충분히 답하고, 확인할 수 없는 내용은 구분하여 안내합니다. 부분 답변 문항 전체를 거절하거나 없는 내용을 만들어내지 않습니다. |

세 항목을 각각 통과/실패로 기록하고 **세 항목을 모두 통과한 경우에만 해당 문항을 최종 통과**로 판정합니다. 답변 불가 문항은 불필요한 인용 없이 확인 불가를 안내하면 인용 기준을 충족한 것으로 봅니다.

Ragas 점수는 최종 통과 판정과 별도로 저장하고 원인 분석에 활용합니다. 적용할 수 없는 지표는 값을 임의로 채우지 않고 적용 불가 사유를 기록합니다. 평가 실행 오류도 정상적인 점수나 품질 실패와 구분하여 기록합니다.

## 7. 기록 방식

RAG 실행은 `output/rag_runs/<rag_run_id>/`, 저장된 답변의 평가는 `output/eval_runs/<eval_run_id>/`로 분리합니다. 각 실행에 공통 `manifest.json`과 문항별 JSON을 저장하며, 평가 폴더에는 `summary.json`과 `summary.csv`도 생성합니다. 골든 파일·스키마·Judge 프롬프트 위치와 상세 필드 계약은 [상세 평가 설계](EVALUATION_SPEC.md)에 확정했습니다. 같은 답변을 재평가할 때는 새 평가 ID를 발급하고, 사람 판정은 검토 이력으로 추가합니다.

### 문항별 JSON에 남길 내용

- 실행 식별자와 문항 ID
- 질문, 기대 답변, 근거 위치, 기대 답변 가능 유형, 평가 기준
- 문서·청킹·검색·모델·프롬프트 등 재현에 필요한 실행 설정
- 검색 결과의 본문·식별자·페이지·정정 구분·순위·거리 등 확보 가능한 정보
- 생성 모델에 실제 전달한 컨텍스트와 최종 자연어 답변
- 실행 상태와 오류 정보
- Ragas 점수와 확보 가능한 평가 근거, 적용 불가 사유
- 규칙 검사와 LLM Judge의 항목별 판정 및 이유
- 실제 답변 가능 동작에 대한 판정과 기대 유형 일치 여부
- 사람의 항목별 판정·최종 판정·원문 대조 근거·자동 평가와의 불일치 이유
- RAG 실행과 자동 평가 각각의 토큰 사용량·비용·소요 시간

### 전체 CSV에 남길 내용

한 행에 한 문항을 배치하고 문항 ID, 주제, 기대 유형, 실행 상태, 자동 판정, 사람의 세 항목 판정, 최종 통과 여부, Ragas 점수, 불일치 요약, 비용·시간, 상세 JSON 위치를 비교할 수 있도록 정리합니다.

긴 검색 본문과 답변 전문, 상세 평가 이유는 JSON에서 확인합니다. CSV에는 문항별 결과를 비교하는 데 필요한 요약을 담습니다.

### 비용과 응답 시간

사용자에게 답변하는 RAG 실행과 그 답변을 채점하는 자동 평가의 비용·시간을 분리합니다. 첫 실행에서는 측정값을 수집하고, 허용 기준은 결과 확인 후 정합니다. **첫 평가의 통과 조건에는 비용과 응답 시간을 포함하지 않습니다.**

## 8. 대표 실패 분석

대표 실패 사례에 대해 다음 순서로 원인을 확인합니다.

1. 원문에 답변에 필요한 근거가 있었는지 확인합니다.
2. 검색이 필요한 근거를 찾았는지 확인합니다.
3. 표 제목·단위·열 이름 등 해석에 필요한 맥락이 보존되었는지 확인합니다.
4. 실제 전달 컨텍스트에 필요한 근거가 포함되었는지 확인합니다.
5. 생성 답변이 금액·단위·정정 시점을 정확히 반영했는지 확인합니다.
6. 각 인용이 연결된 주장을 뒷받침하는지 확인합니다.
7. 답변 가능 범위를 올바르게 판단했는지 확인합니다.
8. 자동 평가와 사람의 판정이 다르면 그 이유를 기록합니다.
9. 가장 먼저 개선할 대상을 제안합니다. 실제 개선 적용과 재평가는 선택 사항입니다.

## 9. 확정 사항과 남은 작업

- 확정: 질문 10개와 골든 답변·근거·조건, Ragas 4개 지표와 문항별 입력·적용 범위.
- 확정: 규칙 검사와 Judge의 역할, Judge 고정 모델·프롬프트·출력 형식.
